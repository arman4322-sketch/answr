1 · System overview & architecture

Answr is an Answer Engine Optimization (AEO) analytics platform: it measures how a brand appears in AI assistant answers (ChatGPT, Claude, Gemini, Perplexity, Google AI Overviews), traces the citations behind those answers, tracks AI crawlers hitting a site, and turns gaps into a scored action queue.

It is a single Next.js 16 App Router application (one deployable) with three concerns: a public marketing site, a gated analytics dashboard, and a backend "engine" of server routes and library modules. Pages are React server components by default; interactivity lives in small "use client" leaf components. There is no separate backend service — API routes and the engine run inside the same Next.js deployment.

Engine layers

Presentation — 73 routes (marketing / dashboard / auth), 28 shared components, a token-based design system.
API — 16 server routes (auth, telemetry, lead/waitlist, prompts/actions, sampler, scoring, integrations).
Domain logic — scoring (answers → metrics), sampler (run providers), telemetry aggregation, export/report engine, filter/window engine.
Integrations — provider clients (Perplexity, OpenAI, Anthropic, Gemini, DataForSEO) behind a uniform interface + registry.
Persistence — a generic document store: in-memory now, durable Redis/KV when a credential is set (same interface; Postgres-ready).

Design principle throughout: works in-memory now, becomes production-durable when a storage key is added — no code change. Provider- and storage-dependent features are written and wired but inert until a key is present, so the platform runs end-to-end with zero external accounts.

5 · The engine (data & logic layers)

Persistence — lib/db

A generic document store with a single Db interface (list / get / put / remove over named JSON collections). MemoryDb runs with zero setup; KvDb speaks the Upstash REST protocol via fetch. db() auto-selects the durable store when KV_REST_API_* or UPSTASH_REDIS_REST_* is set, else memory — no code change. entities.ts defines the typed tables (workspaces, users, sessions, prompts, actions, leads, view events), each tenant-scoped by workspaceId. real

Authentication — lib/auth

A complete account system on Node crypto: scrypt password hashing (salted, timing-safe), opaque session tokens, and user/session records in the data layer. Powers /api/auth/{signup,login,me,logout}. The dashboard layout validates sessions server-side. real

Scoring — lib/scoring

Pure functions that turn sampled answers into the metrics defined in lib/metrics.ts: position-weighted visibility score, share of voice, citation counts, owned-citation share, average answer position, and rank-first. Demonstrable at /api/scoring/preview. real

Sampler — lib/sampler

The nightly job: reads the tracked prompt set, runs every configured provider against each prompt, normalizes answers + citations, and writes runs to the answer store (memory + KV). Triggered by the Vercel cron → /api/runs/execute. Refuses to run without a secret so it never spends provider credits unattended. activates with keys

Provider integrations — lib/providers

A uniform AnswerProvider interface (sample(prompt) → { text, citations }) with thin clients for Perplexity, OpenAI, Anthropic, Gemini, and DataForSEO, plus a registry that reports which are configured. Each reads its env key and is inert until one is present. activates with keys

First-party telemetry — lib/telemetry + proxy.ts

The one pipeline producing real (non-fixture) data today: proxy.ts → /api/ingest → store → /app/live. Captures AI crawlers hitting the site (which never execute JavaScript) and, via public/snippet.js + /api/collect, AI referrals. real

Export & filters

lib/export is a real CSV report engine (titled envelopes, executive summary, per-module specs) used across ~30 controls. lib/filters is a deterministic date/platform windowing engine that re-slices charts and honestly discloses the export window. real

7 · Data model & storage

All records are JSON documents in named collections, keyed by id, tenant-scoped by workspaceId where relevant.

EntityCollectionKey fields
Workspaceworkspacesid, name, domain
Userusersid, email, passwordHash (scrypt), workspaceId
Sessionsessionsid (token), userId, workspaceId, expiresAt
Tracked promptpromptsid, workspaceId, text, intent
Action itemactionsid, workspaceId, title, impact, effort, status
Leadleadsid, email, company, source, utmSource, referrer
View eventviewsid, page, source, ts (waitlist funnel)
Crawler / referral eventtelemetrybot, path, status, verification (first-party capture)
Prompt run / answersamplerprompt, per-provider text + citations (sampler output)

Storage backends: in-process memory (default) or Redis/KV (when a credential is set), selected automatically behind the same interface. The design is Postgres-ready — a Postgres implementation of the Db interface drops in without touching callers.

9 · Running locally

Prerequisites: Node 22.x. No database or keys needed for the demo.

npm install
npm run dev        # dev server (defaults to port 3000; project launch config uses 3201)
npm run build      # production build
npx tsc --noEmit   # type-check

Open the app, go to /login, and sign in with the demo passphrase (default dana@nike.com / answr-demo) to reach the dashboard.

10 · Deployment

Deployed on Vercel with GitHub auto-deploy: a push to main builds and promotes to production; branches get preview URLs. vercel.json schedules the nightly sampler cron. Node is pinned to 22.x. To deploy under a new account: connect the repo to a Vercel project, set the desired environment variables, point the domain, and push.

11 · Security model

  • Access gate — /app/* is protected. proxy.ts does an edge-safe cookie presence check; the dashboard layout then validates for real, granting access by either the demo passphrase or a valid account session, and bouncing invalid sessions.
  • Authentication — scrypt password hashing (salted, timing-safe), opaque session tokens, HTTP-only cookies. A security review is recommended before production reliance.
  • Ingest hardening — the telemetry ingest endpoints accept a shared secret (ANSWR_INGEST_SECRET) and check origin; set the secret in production.
  • Sampler safety — the sampler refuses to run without CRON_SECRET, so provider credits are never spent unattended.
  • Secrets — none are committed; all live in the deployment environment.

12 · How to extend it

TaskHow
Add an AI providerImplement the AnswerProvider interface in lib/providers, add it to the registry array — the Integrations UI and sampler pick it up automatically.
Add / change a metricEdit lib/metrics.ts (definition + formula) and the corresponding function in lib/scoring.
Swap to PostgresImplement the Db interface (lib/db) over Postgres; no caller changes.
Add a pageCreate a page.tsx in the appropriate route group; it inherits that group's shell.
Wire scoring into a dashboardRead accumulated runs from the answer store, call scoreRuns(), and render in place of the lib/data/* fixture for that screen.
Turn on real account accessMake lib/auth sessions the sole gate for /app (JWT-at-edge or the existing node layout guard) and retire the demo passphrase.

13 · Build, quality & testing

  • Type-safe — tsc --noEmit passes with zero errors; no page is a client component.
  • Clean build — next build generates 78 static pages with no warnings.
  • Honesty layer — ~110 inert controls each state what they would do on a live workspace, rather than failing silently — an unusually disciplined pattern that aids both users and maintainers.
  • Accessibility — landmarks, a skip link, keyboard focus rings, ARIA on interactive widgets, reduced-motion support.
  • SEO — native robots.txt, sitemap.xml, Open Graph image, and per-page metadata.

There is no automated test suite; verification to date has been type-checking, clean builds, and manual/functional checks. Adding tests around the engine (scoring, providers, db) is a reasonable early investment for the new owner.

14 · Known limitations & notes for a new team

  • Demo vs live data — most dashboard numbers are the curated "Nike" fixture; they become real once providers are connected and scoring is wired into the views (see LAUNCH_ROADMAP.md).
  • In-memory default — without a storage key, data resets on serverless cold starts and is not shared across instances. Set a Redis/KV key for durability.
  • Provider clients — written against documented endpoints but not run against live keys; verify each with a real key (the Integrations "Test connection" button exists for this).
  • Access gate — the demo passphrase still governs /app; switching to real account sessions is the documented last wiring step.
  • Dev-only quirk — in local dev, server-rendered pages and API routes are separate module graphs, so in-memory writes via an API route aren't visible to a page render; this disappears with a durable store and in production.
  • Conversation / demand panel — panel-grade conversation metrics require a licensed data contract; until then they should be labeled "modeled / beta."
